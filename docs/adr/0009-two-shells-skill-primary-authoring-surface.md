# Layer 2 runs as two shells over one kernel; the skill is the primary authoring surface

The newsletter agent (and the pattern for future Layer 2 agents) runs as two thin shells over one kernel. The kernel is the Django `fundraising` app: the spine models, the Tool Belt services, and a new **Editorial Layer**, markdown files in `fundraising/voice/` (`voice_guide.md`, one `structure-<type>.md` per issue type, `qa_checklist.md`) that hold ALL voice and structure knowledge. Shell 1, the primary authoring surface, is the `masi-newsletter` Claude Code skill grown into a Newsletter Studio: any source (Airtable story, voice note plus photos, an Instagram post Jim loves, a stats brief), any of the four issue types (child/youth story, results/impact update, campaign/appeal, news/milestone), Jim in the loop per issue. Shell 2 is the `draft_newsletter` cron, kept as the organization-owned headless path; `compose.py` shrinks to plumbing that reads the same editorial files.

Why: newsletter production splits into constraints that never vary per issue (voice, template, never fabricate, no naked numbers, draft-only writes, record in spine) and judgment that varies every issue (which story, which type, whether stats strengthen or clutter, what angle). Code is the right medium for constraints; a model in conversation with Jim is the right medium for judgment. The empirical signal arrived within two sessions: the pipeline accumulated `--count`, `--stat-key`, `--cta-text`, `--cta-url`, a structural pivot from three stories to one, and a queue of source types it could not ingest. Jim's real trigger is also conversational ("I love this Instagram post", a voice note after a school visit), which a cron tick cannot see, and he reviews every send regardless (ADR 0003), so headless autonomy was not buying quality. This is ADR 0006 taken at its word: the first Layer 2 agent was accidentally written in the expensive medium (Python orchestration); the disposable part is being re-expressed in the cheap one (skill instructions), while every guarantee stays in the tools.

Concessions absorbed from the rejected keep-rails-separate option (steelmanned before deciding): (1) the cron reads editorial files from *deployed* code, so session experiments cannot leak into a scheduled send until a deliberate deploy: version pinning for free, no extra machinery; (2) `draft_newsletter` survives as the delegable path that does not depend on Jim's laptop or Claude Code tooling; (3) self-improving-loop metrics (ADR 0007) are computed per shell, and autonomy-dial promotion evidence comes from the frozen cron shell only, because a conversationally-tweaked skill is a moving target you cannot measure against.

Consequences: every composed newsletter, one-offs included, must land in the spine. This is enforced mechanically, not by instruction: a new `record_and_draft` command writes the Draft row and creates the Mailchimp draft campaign in one transaction, and it becomes the only Tool Belt path to Mailchimp (the same make-the-wrong-thing-impossible trick as no-naked-numbers via PublishedStat). Editorial rules live in exactly one place; when Jim's red pen identifies a durable rule rather than a one-off edit, the skill writes it into the editorial files in the same session (ADR 0007's generative direction running live). The stats catalog (`/api/impact/published-stats/` now, `metrics.compute` when built) is the only permitted source of numbers for both shells. Discipline required: the skill must never grow inline guarantees or private rules; when it needs capability, the answer is a tool or an editorial file, per ADR 0006.

Channel generality (Jim, same session): the kernel is channel-agnostic by construction. The story is the atom; a newsletter issue, a Personal Send, a LinkedIn post, or a social caption are renderings of that atom for a channel x audience pair. What varies per channel lives in the swappable parts (a structure file per channel, a renderer per channel, audience-aware stat *selection* guidance); what stays constant lives in the kernel (the story, never fabricate, the stats catalog, spine recording). `Draft.kind` already enumerates channel artifacts, so `record_and_draft` takes a kind rather than hard-coding newsletter. Guard against over-engineering: name the seam, build nothing. Mailchimp email remains the only built renderer; nothing outside `render_email` and the Mailchimp client may assume "email"; social stays propose-only per the existing boundary (staff run socials; agent drafts feed the Content Calendar's "Proposed by AI" rows).

Considered: keeping the rails fully separate for a quarter (a firewall between tested cron and creative sessions, and cheap evidence-gathering; rejected because it duplicates editorial rules across two prompt surfaces exactly when copy quality is the bottleneck, though its two strongest arguments were absorbed as concessions above). Making the Django pipeline flexible instead (issue-type configs, source adapters, an Instagram ingester; rejected: it rebuilds a conversational judgment engine in Python, the slowest path, and fights the per-issue nature of editorial decisions).
