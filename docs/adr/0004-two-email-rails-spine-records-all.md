# Two email rails — Mailchimp broadcasts and Gmail personal sends; the spine records everything

Outbound email runs on two deliberately different rails. Broadcasts (the newsletter, ~500 subscribers) go through Mailchimp: the Marketing Agent assembles the issue from the content library and pushes it via the Mailchimp API as a draft campaign; Jim reviews and sends inside Mailchimp. Personal Sends (big-donor updates, and later Steward thank-yous) are one-to-one emails from Jim's own mailbox: agents create Gmail drafts; Jim reviews in his inbox and sends. Personal notes and message history on donors live in the spine with a privacy flag — "personal" is access control, not storage location. A Gmail sync restricted to email addresses of tracked Contacts logs sends and replies as Interactions; mail to non-Contacts is never read.

Why: 1:1 mail from a real mailbox lands in Gmail Primary with roughly double the open rate of ESP mail, which lands in Promotions — for a handful of major donors, Jim's inbox beats any ESP. Mailchimp is kept (rather than migrating to a developer ESP like Resend) because the list already lives there, the editor is a manual escape hatch, and the actual gap being fixed is content assembly and cadence, not delivery. All rails write Interactions so the CRM records itself.

Considered: Resend + React Email as a single programmatic rail for both shapes — cleaner API, templates as code, webhook logging. Rejected for v1 to avoid migration and because the personal rail must be Jim's real mailbox regardless. Revisit if broadcast volume outgrows Mailchimp's API ergonomics or when receipts/transactional volume grows.
