# The Tool Belt is the durable asset; agents are thin, disposable compositions

The system is built as two layers. Layer 1 is a small, well-tested **Tool Belt** — functions that read the spine (`contact.history`, `opportunity.context`, `content_use.history`), supply curated knowledge (`published_stats.pick`, `answer_library.select`, `funder_brief.read`, `voice_guide.read`), write drafts (`draft.create`, `interaction.propose`), and drive the edges (`gmail.*`, `mailchimp.*`). Layer 2 is the agents (Newsletter, Grant Studio, Morning Brief, Funder Research), each a thin orchestration of Tool Belt calls plus a prompt. Agents never reach around their tools to query the database or call an external API directly.

Why: capability and correctness live in the tools, which are tested once and shared; intelligence and sequencing live in the agents, which are cheap to rewrite. A new agent nobody has imagined yet should be buildable almost entirely by composing existing tools. This is the inversion of the usual instinct to make each agent self-contained — here the agent is the disposable part. `published_stats.*` already exists in production on `/impact`, so the belt is real on day one, not aspirational.

Consequences: discipline is required — when an agent needs data, the answer is a new or extended tool, not an inline query, even when inline would be faster this once. The tool surface stays deliberately small; sprawl in the belt defeats the purpose. Because every number flows through `published_stats`, ADR 0005's "no naked numbers" rule becomes mechanically enforceable. The same tools serve agents we will write later (e.g., a board-report generator) without new plumbing.

Considered: per-agent bespoke data access (faster to ship one agent, but every later agent re-pays the integration cost and the stale-number firewall cannot be enforced centrally). Rejected because the whole premise — Jim's words — is that tools are the durable asset and agents are not.
